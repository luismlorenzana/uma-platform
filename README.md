# Uma Platform

The shared foundation for the owner's personal Uma games: **uma-racer**, **uma-rpg** and **uma-puzzle**. Personal and
never distributed.

It owns:

- **Master data.** Uma characters with full stats, support cards, skills, scenarios and art, imported once and
  published as private releases that every game reads.
- **Shared packages.** Code every game uses the same way, published privately to GitHub Packages.
- **Original art.** Tilesets, maps, UI and effects made for these games, generated by scripts.
- **The cross-game plan.**

## Status

Phases 0 and 1 are done, and Phases 2 (uma-rpg) and 3 (the uma-racer refactor) are in progress.
`@luismlorenzana/uma-data` and `@luismlorenzana/uma-art` are on GitHub Packages: uma-rpg uses both, and uma-racer
installs `uma-data`. `@luismlorenzana/uma-kit` (P48) is the app both games share: theme, primitives, shell, Hub
map, sign-in and the place frames (P56). `@luismlorenzana/uma-work` (P53) is the work engine both games run, and `@luismlorenzana/uma-server` (P54) the
NestJS pieces both APIs share. See the [roadmap](docs/roadmap.md).

## Develop

Node 22 and pnpm 10 (`corepack enable`).

```bash
pnpm install
pnpm lint     # type-check every package
pnpm test     # Vitest, synthetic fixtures only, no network
pnpm build
```

The Uma Platform app runs locally on two dev servers (`.claude/launch.json`: `platform-api` on 8111 with sign-in off,
`platform-web` on 5204), reading master data from `content/release`. A push to `main` that touches `apps/` or a package
it uses deploys it (`.github/workflows/deploy-app.yml`).

## Make a master data release

```bash
pnpm data:import                 # GameTora datasets → content/release/data/*.json
pnpm assets:import               # images → atlases, art and the art index
pnpm release:publish -- --dry-run
pnpm release:publish             # files → manifest → channels/v1/latest.json
```

For a new banner, [docs/new-umas.md](docs/new-umas.md) has the whole path: `pnpm uma:check`, `pnpm uma:import`, review,
publish, and how to undo it.

**Sprite sets** publish on their own, on top of the published `latest`, once the owner approves a batch in the Studio
([pipeline.md](docs/sprites/pipeline.md) §7, "Publishing a batch"):

```bash
pnpm sprites:pack                                                    # approved sets → content/release/
pnpm release:publish -- --sprites-only --channel candidate           # every other file carried byte for byte
pnpm release:check -- --channel candidate --against latest           # read it back like a game
pnpm release:publish -- --promote <version>                          # then move latest
```

**Enemies** (the `enemies` roster and the `enemy-keys` family, uma-quest Q16, P152) publish the same way, on top of
`latest`, once the owner approves an enemy's set review ([enemy-keys.md](docs/sprites/enemy-keys.md) §10):

```bash
pnpm enemies:pack                                                    # the boards' roster and approved keys → content/release/
pnpm release:publish -- --enemies-only                               # to candidate; every other file carried byte for byte
pnpm release:check -- --channel candidate --against latest
pnpm release:publish -- --promote <version>
```

**A new art family** (an additive one, like `outfit-renders`, P137) publishes the same way, on top of `latest`:

```bash
pnpm assets:import -- --families=outfit-renders                       # GameTora → content/release/
pnpm release:publish -- --add-families=outfit-renders --channel candidate
pnpm release:check -- --channel candidate --against latest --added-families=outfit-renders
pnpm release:publish -- --promote <version>
```

The first run on a machine needs the private inputs (P31): `content/overrides/scenario-icons.json` and the owner's
wiki art folder, staged once with `pnpm assets:import -- --source dir:~/Documents/uma-content`. Downloads are cached
in `scripts/*/.cache/`, so later runs only fetch what's new. Publishing uses the owner's `default` gcloud
configuration through environment variables and never changes the active one (see [infra/README.md](infra/README.md)).

## Use `@luismlorenzana/uma-data` in a game

The package is private on GitHub Packages. In the game repo, add an `.npmrc` (commit it; it holds no secret):

```ini
@luismlorenzana:registry=https://npm.pkg.github.com
//npm.pkg.github.com/:_authToken=${NODE_AUTH_TOKEN}
```

**Locally**, the gh token needs `read:packages` once (`gh auth refresh -h github.com -s read:packages`), then:

```bash
NODE_AUTH_TOKEN=$(gh auth token) pnpm add -E @luismlorenzana/uma-data
```

**In CI**, give the workflow `packages: read` and pass the job's token:

```yaml
permissions:
  contents: read
  packages: read
steps:
  - uses: actions/setup-node@v6
    with:
      node-version: 22
      cache: pnpm
  - run: pnpm install --frozen-lockfile
    env:
      NODE_AUTH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

A game repo's `GITHUB_TOKEN` can read the package only after the package grants that repo access: on GitHub, open the
`uma-data` package (and each other package it installs: `uma-art`, `uma-kit`, `uma-work`, `uma-server`) → **Package settings** → **Manage
Actions access** → add the game repo with the **Read** role.

**Reading releases.** Each game's API reads the private bucket with its own read-only service account and serves the
files to its web app through its logged-in endpoint (architecture §2.2):

```ts
import { createReleaseClient, type ReleaseSource } from '@luismlorenzana/uma-data'
import { Storage } from '@google-cloud/storage'

const bucket = new Storage().bucket('uma-platform-master-data')
const source: ReleaseSource = {
  read: async (path) => new Uint8Array((await bucket.file(path).download())[0]),
}
const { manifest, data, art } = await createReleaseClient({ source }).load() // latest within schema major 1
```

In the web app, `createFetchSource({ baseUrl: '/api/master/', init: () => ({ headers: { authorization } }) })` reads
the same paths through the API. Tests use `@luismlorenzana/uma-data/testing` (`syntheticMasterData`,
`buildMemoryRelease`, `createMemorySource`). Field reference: [docs/master-data.md](docs/master-data.md).

Depend on an exact version (`pnpm add -E`) and upgrade on your own schedule (P9). Within schema major 1 the client
accepts every newer release, so new characters, cards and skills arrive without a code change (P7).

## Releasing a package

1. A change to `packages/*` comes with a changeset: `pnpm changeset` (minor for additive schema changes, major for
   breaking ones; see AGENTS.md).
2. On `main`, `pnpm version-packages` bumps versions and writes the changelog; commit and push.
3. The **Release packages** workflow publishes every version not yet on GitHub Packages, using the workflow's
   `GITHUB_TOKEN` with `packages: write`, and pushes the release tags.
